# Blogging workflow

How a post gets from an idea to a live URL on jains.es. Written for whoever
does this next, human or agent. `CLAUDE.md` holds the prohibitions; this file
holds the process.

## The short version

```bash
npm run post "The title of the post"   # scaffolds content/posts/the-title.md
# write it
npm run build                          # validates, generates, builds
git add -A && git commit && git push   # push to main deploys
```

One Markdown file per post. Everything else — the post page, the blog index,
the topic page, `sitemap.xml`, `feed.xml`, the homepage list, the related-posts
block and all the schema — is generated by `build/site.js`. There is nothing
else to update, and hand-editing any generated file lasts until the next build.

## The file

```
---
title: Sentence-case title, no trailing full stop
description: One sentence, ~155 chars. Meta description and RSS description.
ogTitle: Shorter title for link previews
ogDescription: One short sentence for link previews
date: YYYY-MM-DD
category: retail-tech | hrtech | edtech
sources:
  - primary | Publisher | YYYY-MM-DD | Exact title | https://...
  - reported | Publisher (Reporter) | YYYY-MM-DD | Exact title | https://...
---

Body in Markdown. `##` for headings — never `#`, the h1 comes from the title.
Do not write a Sources section; the build renders one from the front matter.
```

If a title contains a colon, wrap the value in single quotes. The front-matter
parser is a small subset of YAML — `key: value` lines and the one-per-line
`sources:` list — so it does no escaping. A quoted title containing an
apostrophe will render the quotes literally. Avoid colons in titles instead.

**The filename is the URL.** `content/posts/learning-debt.md` serves at
`/blog/learning-debt/`. Renaming a live post 404s an indexed page. Don't.

## Categories

| slug | display name | what belongs in it |
|---|---|---|
| `retail-tech` | Retail and commerce tech | commerce tech, storefronts, payments, supply chain, retail media, AI reaching retail operations |
| `hrtech` | Work and talent tech | hiring tech, HR systems, skills, workforce analytics, AI in hiring and its regulation |
| `edtech` | Learning and training tech | corporate L&D, training platforms, credentialing, edtech funding read as a buyer signal |

The slugs are industry nouns because that is what readers search for; the
display names are the fuller description. Both are permanent once a topic page
is live. AI is a thread running through all three, never its own category — a
standalone AI bucket would swallow most posts and tell a reader nothing.

Adding a fourth category means a new topic page, a new URL and a decision.
Ask first. Edit `CATEGORIES` at the top of `build/site.js`.

## What the build refuses to ship

`node build/site.js` exits 1 — and the post does not generate — on:

- an unknown `category`
- a `date` that isn't `YYYY-MM-DD`
- a duplicate slug
- a post with no sources
- a source line without exactly 5 pipe-separated fields
- a source whose tier isn't `primary` or `reported`
- a source missing a publisher, a valid date, a title, or an `http(s)` URL

This is deliberate. Fix the post; never work around the check. A provenance
badge applied only when someone remembers is worse than no badge at all.

## Source tiers

- **primary** — the regulator, vendor, paper, survey or filing *itself*
- **reported** — a named outlet reporting a fact first (Reuters, FT, HR Dive,
  Retail Dive, TechCrunch…), ideally with the reporter named in the publisher
  field

The tier describes **the URL**, not the organisation that produced the data.
A Conference Board survey reached through an HR Dive article is `reported`,
publisher HR Dive — not `primary`, publisher The Conference Board. Getting
this backwards is the single easiest way to make the site less trustworthy
than having no tiers, and it has already happened once.

**A post must never predate a source it cites.** Check the latest source date
against the post date before shipping.

**If a source cannot be dated** — the journal blocks crawlers, the page is a
living reference with no publication date — do not substitute the date you
accessed it. Cite it as an inline Markdown link in the prose, where no date is
claimed, and leave it out of the front matter.

## Writing standard

Inverted pyramid, BBC/Reuters discipline, senior practitioner audience — a
retail operations director, an HR or talent lead, an L&D head. Not technical,
not naive, holds a budget, can smell a vendor pitch.

- **First paragraph carries the whole story.** What happened, when, why this
  reader should care. Someone who stops after paragraph one still got the
  point. No scene-setting, no rhetorical question, no "in today's landscape".
- **Attribution inline, always.** "according to the FTC's August policy
  statement", "BambooHR's survey, reported by HR Dive on 2 September". Every
  statistic carries a named publisher and a date **in the prose**.
- **A number without a traceable source gets cut**, not softened to "studies
  suggest" or "research shows". This is the rule that does the most work.
- **Land somewhere useful.** What this reader should do, decide or check in
  the next quarter. A post that only summarises the news has failed.
- **Legal care.** A proposed rule is not a rule. A denied motion to dismiss is
  not a finding of liability. A postponed obligation is not a repealed one.
  Say what has and has not been decided; write what a leader should ask their
  counsel, never advice.
- 800–1,200 words. If there are only 700 words of substance, write 700.
- British spelling, to match the existing posts. Exceptions: official terms
  (the FTC's "personalized pricing") and verbatim source titles.
- No hype, no "game-changer", no triads of adjectives, no closing paragraph
  that restates the opening. Never pitch in the body — the build appends the
  CTA.

Run the `no-ai-slop` skill over every draft.

## Research, when posts are news-anchored

The process that produced the September 2026 batch, worth repeating:

1. **Research to a list, not to drafts.** Find candidate developments inside a
   stated window with verified, reachable sources. Record each as: what
   happened, its date, the proposed angle, why it earns a post, the category,
   and the source lines in the exact front-matter format.
2. **Gate on the list.** A human strikes the weak ones *before* anything is
   drafted. This is the cheap review; skipping it means rewriting finished
   posts.
3. **Let counts follow the material.** If a category only yielded five
   substantial items, write five. Padding to hit a number produces exactly the
   posts a senior reader stops trusting you over.
4. **Reject "nothing much changes for you yet."** If the honest angle is that,
   there is no post.
5. **Draft, then review against the sources**, not just for voice. Check the
   tiers, check no post predates its sources, check every number traces.

`content/research-candidates.md` is the working artefact from that batch. It is
gitignored — it is an input to review, not site content.

## Cross-linking

Every post automatically gets its topic page link, three related posts from the
same category, and a link to the index. That handles orphaning. Hand-written
links are for connections the generator cannot infer — two posts that are the
same problem from different directions. Don't manufacture them.

Project links (`guldaarbazaar.com` and the rest) are external domains. Link
them where a post genuinely references the work, but they pass authority out,
not in. `/#work` and the topic pages are the internal targets that help.

## Verifying before you push

```bash
npm run build          # must exit 0
npm run dev            # check a post, the index, a topic page
```

Pushing to `main` deploys via Cloudflare Workers Builds, usually within a
minute. A failing build leaves the previous version live. After a deploy:

```bash
curl -s https://jains.es/sitemap.xml | grep -c "<loc>"
curl -o /dev/null -w '%{http_code}\n' https://jains.es/README.md   # 404 is correct
```
