# jains.es

Read README.md first — layout, how to add a post, how deploys work.
**BLOGGING.md** is the posting workflow: front matter, source tiers, the
writing standard, the research-then-gate process. **AI101/WORKFLOW.md** is the
daily pipeline: what runs when, which prompt, which skill, what it produces.

This file is only the things that are easy to get wrong and expensive to undo.

## What this site is now

A daily learning publication — one person building LLMs from scratch in public,
India-primary and Global South audience, many of them ESL, ages 17 to 68. The
agency is a section of it, not the point of it. `AI101/PLAN.md` is the design.

## Never

- **Never edit anything under `blog/`, `wiki/`, `day/`, `public/sitemap.xml` or
  `public/feed.xml`.** All are generated by `build/site.js` and are gitignored.
  Edit the Markdown in `content/` instead; the next build overwrites your
  changes.
- **Never edit the block between `<!-- generated:posts -->` and
  `<!-- /generated:posts -->` in `index.html`.** Same reason.
- **Never change a post's filename once it is live.** The filename is the URL.
  Renaming it silently 404s an indexed page. The same applies to a wiki slug.
- **Never renumber a lesson.** `day:` in the front matter is the URL, and it is
  declared rather than counted precisely so that a missed day cannot shift every
  later lesson onto a new address.
- **Never add page entries to `vite.config.js`.** It globs `blog/`, `wiki/` and
  `day/`.
- **Never hand-edit DNS records for jains.es or www.jains.es.** Wrangler manages
  them through `routes` in `wrangler.jsonc`.
- **Never add a `main` script to `wrangler.jsonc`.** Without one the site is
  served purely from asset storage and uses no request quota.
- **Never set `workers_dev: true`.** It publishes an indexable duplicate origin.
- **Never commit `dist/`.**
- **Never reintroduce the custom cursor.** Removed deliberately; replacing the
  native pointer is an accessibility cost for a flourish most visitors never
  see, and the traffic is overwhelmingly mobile.
- **Never add a contact form.** One was built and removed (c0f88b3). Contact is
  a WhatsApp link and a mailto. This has not changed — see the reversal below,
  which covers the subscribe form only.

## The one reversal, and why

The old rule read *"never add a form, an input, a textarea or a newsletter
signup."* It was written for an agency one-pager where a contact form was
noise. This is a publication now, and email is the only distribution asset that
survives a platform changing its mind. **A subscribe form is intended design.**

Recorded so no future agent reinstates the prohibition by reading old commits.

The contact half of the old rule still stands, immediately above.

## The subscribe form

- **One constant owns the address.** `SUBSTACK` at the top of `build/site.js`.
  Every footer on the site is generated from it, including the ones inside the
  hand-written pages, which carry `<!-- generated:footer -->` markers. Never
  paste the URL into a page.
- **It is a plain `<form method="get">` pointing at Substack**, with one
  `type="email"` input. Substack prefills its own subscribe page from the
  `?email=` query parameter — verified live, not assumed.
- **Never replace it with Substack's iframe embed.** Measured: 96 KB of HTML,
  115 requests, 90 JavaScript files, 5 cookies, and calls to `js.sentry-cdn.com`
  and `static.cloudflareinsights.com`. In a footer that lands on every page,
  against a 150 KB budget, for readers on low-tier Android.
- It needs `form-action 'self' https://*.substack.com` in `public/_headers`.
  That is the only CSP relaxation it requires. Do not widen `script-src`,
  `connect-src` or `frame-src` for it.

## Article pages ship zero JavaScript

Low-tier Android is roughly 9× slower than a development machine, so script
costs bytes *and* main-thread time on exactly the device this audience holds.

- Posts, lessons and wiki pages carry **no `<script>`** beyond `ld+json`, which
  is data and never executes.
- The theme follows `prefers-color-scheme` in pure CSS. The **toggle** ships
  only on pages that already carry the bundle.
- Dark mode is `#e6e6e6` on `#16181c`. **Never white on black** — it maximises
  halation for readers with astigmatism.
- Note when touching this: `src/main.js` imports `styles.css`, so today the
  stylesheet only exists as a side-effect of the JS bundle. Decouple that first.

## Mobile first

The stylesheet is mobile first: base rules are the phone layout, and two
`min-width` blocks (441px, 901px) add what larger screens can afford. Write new
rules the same way — put the phone case in the base rule, not in an override.
Roughly 90% of the traffic is mobile.

## Adding a post

```bash
npm run post "The title"   # scaffolds content/posts/the-title.md, dated today
npm run build              # validates, generates, builds
```

The build **fails** on an unknown category, a malformed date, a duplicate slug,
or a source missing its tier. That is deliberate — fix the post, don't work
around the check. It is also the strongest control on the site: it blocks an
unsourced claim from ever reaching a page.

Categories are fixed: `retail-tech`, `hrtech`, `edtech`. They apply to
`content/posts/` only. Lessons and wiki pages are separate page types with
their own front matter, not a fourth category. Adding a fourth category means a
new topic page, a new URL, and a decision — ask before doing it.

## The pages, and who owns them

| Page | File | Footer |
|---|---|---|
| `/` | `index.html` | generated into the marker |
| `/work/` | `work/index.html` | generated into the marker |
| `/about/` | `about/index.html` | generated into the marker |
| `/privacy/` | `privacy/index.html` | generated into the marker |
| 404 | `404.html` | generated into the marker |

`#contact` lives on `/work/` only — the global footer is the newsletter now, so
it must not answer to that anchor. The agency's WhatsApp and mailto route stays
on `/work/` where "Start a project" can reach it.

## The three page types

| Source | URL | Sources required |
|---|---|---|
| `content/posts/<slug>.md` | `/blog/<slug>/` | Always |
| `content/wiki/<slug>.md` | `/wiki/<slug>/` | Only at `stage: evergreen` |
| `content/lessons/<date>.md` | `/day/<n>/` | Always |

A seedling may cite nothing — that is what saying it is a seedling buys. An
evergreen page has been audited, so it shows its working.

Wiki and lesson pages ship **zero JavaScript**: `head()` takes `noScript: true`
and emits a stylesheet link instead of the JS entry. The 23 archive posts still
carry the bundle; that is the deferred work, not an inconsistency to tidy.

`npm run check` proves the build still refuses bad input. Run it after touching
validation. A gate that does not fire is not a mechanism.

## Front matter is not YAML

`build/site.js` parses `key: value` lines plus **one** list key, `sources:`.
Any other list hits the `kv` regex and throws. So `tags`, `prereqs` and
`related` are **comma-separated strings**, split at point of use. Do not add a
YAML dependency for this.

## Writing standard

Plain British English. Short sentences, one idea each, under 25 words.
ESL-first. Concrete before abstract — never open with a definition. Every
analogy states where it breaks, in the same paragraph. No idiom, no
pop-culture reference, no pun, no sarcasm.

Every statistic carries a named source inline. A number with no traceable
source gets cut, not softened to "studies suggest".

**On `no-ai-slop`:** run it to detect, and apply only provenance fixes —
replace a generic claim with the number, date, filename or real error already
to hand. **Never** edit formal register, em-dashes or semicolons to sound less
like a machine. Detectors flag non-native English at a ~61% false-positive
rate, and formal register is a competence marker in Indian professional
English. The defence against slop is provenance, not stylistic contortion.

The archive of 23 posts keeps its own register — inverted pyramid, senior
practitioner, BBC/Reuters. See BLOGGING.md. Do not rewrite them to match.
